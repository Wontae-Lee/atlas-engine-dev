# 6. Conventions

This document records the structural conventions that code under
`include/atlas/` follows. New code should match the nearest sibling module
before inventing a new layout.

---

## 6.1 File and Module Layout

```text
- Use #pragma once in headers (not include guards).
- The scalar type is float. Public types are plain (non-template) classes:
  Vector3, Matrix3x3, Quaternion, MaterialProperties, ...
- Headers declare; definitions live in src/atlas/<module>/*.cu, mirroring
  the include/atlas/<module>/ directory layout. All engine translation units
  are .cu and are compiled by nvcc into the `atlas` static library.
- Exception: device-callable code (ATLAS_DEVICE / ATLAS_ALL_DEVICE) must be
  defined inline in the header (Atlas builds without -rdc, so device code
  cannot cross translation-unit boundaries). Hot math primitives are entirely
  header-inline for this reason; see include/atlas/math/.
- Reference example of the .h/.cu split: include/atlas/material/ (declaration)
  and src/atlas/material/ (definition).
- The legacy .h/.hpp template pairs are being removed module by module; do not
  add new ones.
- detail/ subdirectories hold internal helpers (kernels, probe builders,
  caches) that are not part of the module's primary surface.
```

Follow the nearest sibling module's organization. Keep helper types close to
the owner they support, and split them out only when the role is substantial
and clearly named (a kernel, builder, probe builder, interaction, or policy).

---

## 6.2 The Generated Umbrella Header

`include/atlas/atlas.h` is generated by `tools/generate_headers.py`. Do not
hand-edit it. When you add, move, or remove a public header, regenerate the
umbrella so the aggregate `#include` list stays correct.

---

## 6.3 Builder Pattern

Most public types use a nested `Builder` with fluent `.with_*()` setters and a
`.build()` / `.make_host_shared()` endpoint. Write builders in the
`MaterialProperties` style:

```text
- Declare `class Builder;` inside the owning class.
- Declare `class Type::Builder final` after the owning class body, in the same
  header; define its methods in src/atlas/<module>/<type>.cu (builders are
  host-only code).
- Keep `builder()` as a static factory on the owning class.
```

Backend and capacity conventions for specific builders:

```text
- Units are owned by Universe: register with Universe::Builder::with_{source,
  sink,collider,measurer}_units(...); Source/Sink/Collider/VolumeMeasurer take
  the domain via with_universe(...) and borrow the matching UnitField.
- Fluid::Builder owns particle capacity via with_buffer_size(...).
- System::Builder does NOT own particle capacity; capacity belongs to Fluid.
```

## 6.4 Naming and Class Member Order

```text
- Prefer concise, recognizable names; optimize for readable control flow over
  raw name length. Keep member function names short when the class context
  already supplies meaning (prefer apply_collision over accept_and_scatter_pair).
- Distinguish each algorithmic step by name; avoid near-duplicate names that
  differ only by a generic suffix.
- Member functions are ordered: constructors/destructor, core functions,
  setters, then getters.
- Member variables are ordered by type when no nearer sibling layout is more
  specific: bool, integer, floating-point, HostBuffer<T>, then DeviceBuffer<T>.
- A public rename is a breaking change; rename public spellings (types, methods,
  headers) only when explicitly requested.
```

---

## 6.5 Active-Prefix Discipline

Particle storage separates allocated capacity from the live population (see
[02-runtime-objects.md](02-runtime-objects.md)):

```text
- Fluid<T>::buffer_size()    total allocated capacity
- Fluid<T>::particle_count() active dense prefix length
- only [0, particle_count) is active
- Source appends behind the active prefix
- Sink compacts survivors and updates particle_count
```

When writing setup code or tests: set capacity with `with_buffer_size(...)`,
set `particle_count` explicitly when active particles should exist, and never
assume `particle_count == buffer_size`.

## 6.6 Solver Guidelines

```text
- Solver<T> owns protected _universe, _fluid, _searcher; derived solvers reuse
  these members instead of duplicating dependencies.
- DSMC solvers cache DsmcSolverProbe in _probe; SPH solvers cache SphSolverProbe.
  Call make_probe() before device launches when probe data must be refreshed.
- Solver-allocation filtering is passed as a function parameter, not stored in
  a probe.
- Allocation filtering only skips cells outside the selected allocation. It must
  not clear collision statistics or universe state owned by another solver.
- Solver code is performance-sensitive; avoid behavior, memory-layout, or
  ownership changes unless requested.
```

## 6.7 Backend Portability

Summarized from [04-backend-portability.md](04-backend-portability.md):

```text
- Everything compiles with nvcc; ATLAS_DEVICE_SYSTEM selects TBB or CUDA as
  the Thrust device system (the Thrust host system is always TBB).
- Prefer DeviceBuffer<T>, HostBuffer<T>, device_shared_ptr<T>, and
  parallel_for<ExecutionPolicy>(...) over backend-specific code.
- Keep backend-specific paths behind ATLAS_TASKING_CUDA / ATLAS_TASKING_TBB.
- Use the portability macros from core/macros.h for device-reachable code.
- Extend device-callable operator unions when adding a geometry, generator, or
  interaction model.
```

---

## 6.8 Comments

Source-code comments are written only when explicitly requested. When
requested, write them in English, and use Doxygen-style comments for public
APIs or for files that already follow that convention. Keep temporary logging,
counters, assertions, probes, and timing code out of production code unless
requested.

---

## 6.9 Tests

```text
- Place tests under tests/<module>/ to match the public module or subsystem.
- C++ test files are named <subject>_tests.cpp.
- Include <gtest/gtest.h> directly; tests use GoogleTest only.
- Keep shared helpers in tests/utilities/test_utils.h, and local aliases,
  helpers, and fixtures in an anonymous namespace.
- Do not add another test main; GoogleTest provides the entry point.
```
